# Project Plan

Keep this plan concrete. It should help a human or AI decide what to do next, not describe an ideal future.

## Project intent

### Who

Who is experiencing the problem or will use the result?

Be specific enough that we can tell whose needs matter when trade-offs appear.

### Problem

What concrete, observable problem do they have now?

Describe the problem without hiding a preferred solution inside it.

### Approach

What is the current proposed solution?

State the smallest practical approach we believe can solve the problem. Treat it as a working hypothesis, not a permanent commitment.

### Success

What would make this project meaningfully successful?

Make the success condition SMART enough to guide decisions:

- **Specific** — what observable behavior or result should improve?
- **Measurable** — what evidence will show whether it improved?
- **Achievable** — is it realistic with the available time, tools, people, permissions, and budget?
- **Relevant** — does the measure reflect the original problem rather than an easy proxy?
- **Time-bound** — when will we stop and reassess whether the approach is working?

Avoid making a metric prove more than it can.

### Scope

What is this project meant to solve, and what is explicitly out of scope for now?

### Portability and compatibility

Choose the intended level first:

- **Local** — designed for one known environment or user.
- **Reusable** — others in similar environments should be able to adapt it with modest work.
- **General** — intended for broad use across different environments.

Then answer only what is relevant to that intended level:

- What environments should it work in?
- Which dependencies, services, models, APIs, hardware, accounts, or data are required?
- Can another user obtain those dependencies from public or documented sources?
- Are standard protocols, formats, and interfaces used where practical?
- Which important dependencies can be replaced without rewriting the core?
- Are environment-specific details isolated in configuration or adapters, or scattered through the implementation?
- Could a person who did not build it understand how to set it up and adapt it from the repository alone?
- If the author's own machine, accounts, private context, and special environment disappeared, what would stop working?

Do not make a local tool into a framework merely for theoretical portability. The required portability should match the project's intended users and scope.

## Consequential checkpoint

Before completing a major milestone, expanding scope, creating a substantial new mechanism, or starting the next phase, stop briefly and answer:

1. Who are we still solving this for?
2. Does the original problem still exist in the form we described?
3. Is the current approach still the smallest reasonable approach?
4. How does this step move us toward the stated success condition?
5. If we removed this step, what real capability or evidence would be lost?
6. Are we solving the original problem, or mostly solving problems created by our previous solution?
7. If we were starting today with the same goal but without sunk cost, would we still choose this step?
8. Has reality changed enough that the goal, scope, approach, success condition, or portability target should be explicitly updated?

The goal may change. What should not happen is silent drift.
